## 1. 项目一句话 + 与 A 线的关系

**把自己已交付的 Olist 电商 MySQL 数仓，从"人写 SQL 出报表"升级为"自然语言问数 Agent"**：用户用中文提问 → 系统检索口径与历史 SQL（RAG）→ 生成 SQL → 只读执行并自校验 → 返回数字、表格与结论。

与既有简历的承接：Olist 项目（ETL+SQL+Power BI）讲"我建了数仓、定义了口径"；本项目讲"我让数仓能被直接提问"。两者构成"传统 BI → AI 增强 BI"一条叙事线，嵌入主版项目经历区，不开新故事。

## 2. MVP 范围界定

**含（五件套，方向标：10 月中前全部跑通并产出准确率数字；软目标，越快越从容）**：① Vanna+Olist MySQL+云端 API 最小问数闭环；② 自写编排（规划→生成→只读执行→校验，代码可逐行讲）；③ 自纠错 1 轮（报错回填→重写→复跑，有日志）；④ 30 题评估集（pytest，执行准确率）；⑤ README+架构图+git 仓库。

**不含（对齐清单 3.2，无异议）**：多 Agent 流水线、MCP、Docker Compose、Dify 部署、OpenManus 阅读、Streamlit 美化、评估集超 30 题。W3–W4 加法按清单 3.2 优先级执行。

## 7. 评估集设计

- **题量**：30 题（W3 扩 50）。**题型分布**：单表聚合 8 / 多表关联 10 / 时序环比 6 / 排名对比 6——全部映射到 BI 问数真实场景（"黑五 GMV 环比""复购率""TOP 品类"）。
- **准确率口径**：执行结果比对——同一连接分别执行标准 SQL 与生成 SQL，结果集做行级规范化（排序无关化、数值取整容差）后比对。**分母 = 30；分子 = 执行成功且结果一致的题数**；SQL 文本相似度不参与判定。
- **产出**：`eval/report.md`：总准确率 + 分类别准确率 + 失败题归因（生成错误/执行失败/口径不符）。

### 8.1 BI / 实施岗版（A 线主版基线简历用）

电商智能问数Agent（ChatBI） ｜ 个人项目	2026.09

· 将自建电商数仓（9表/155万行）从"人写SQL出报表"升级为自然语言问数：把已验证的指标口径（GMV排除取消订单、客户数按自然人ID、类目英译）固化为口径文档作为问数唯一依据，口径守卫自动检出违规并重写。
· 中文提问后系统自动写SQL、查库并返回数字、表格与结论，全流程经LangGraph状态图编排（生成→执行→校验→总结）；界面为Streamlit多轮对话，按结果形状自动配图（指标卡/折线/条形），支持CSV导出与现场演示。
· 自建30题留出评估集（聚合/关联/时序/对比，问法与训练题不逐字重合），以执行结果行级比对评分，准确率96.7%；全程开源GitHub，含架构图、评估报告与一键复现脚本。

### 8.2 纯 Agent 岗版（千里/去哪儿等参考线简历用）

电商智能问数Agent（ChatBI） ｜ 个人项目	2026.09

· NL2SQL内核采用RAG三路训练（表结构DDL/指标口径文档/已验证问答对）+chroma向量检索，DeepSeek-V3.2生成SQL；以口径注入与few-shot示例调优将抽测准确率从86.7%提升至93.3%。
· 自写编排以LangGraph StateGraph表达（生成→只读执行→自纠错→口径/空结果守卫→总结，条件边回环收敛）；执行层只读双保险=应用层白名单闸（拦DML/多语句/INTO OUTFILE、服务端超时、强制LIMIT）+MySQL仅SELECT账号，DELETE实测被拒。
· 自建30题留出评估集并pytest化执行结果行级规范化比对器，一键复跑准确率96.7%（29/30，唯一失分为比对器保守表示差异、数据实际一致）；Streamlit多轮对话前端自动配图，仓库开源含复现文档。

## 9. 推进协议（v2.1：任务队列 + 弹性推进，无每日排期）

**推进方式**：
- 任务按第 3 节拆解表的依赖顺序组成队列，当前指针始终指向一个任务；完成后由智谱在 PROJECT_BRIEF 进度日志核销（附 hash）并将指针移到下一个任务。

- 每任务 ≤1.5h 当日闭合；任一会话结束前，PROJECT_BRIEF 必须反映最新指针位置——断档恢复时从 brief 读现场，不靠记忆。
- 教学锚点随任务走（做完一个模块配一张概念卡+费曼检查），不再按周排。
